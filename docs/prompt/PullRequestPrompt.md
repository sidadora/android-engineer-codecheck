# PR 本文作成プロンプト・テンプレート

## 使い方

- このファイルの「Claude Codeへの作成指示」以降をまとめてClaude Codeに渡す。
- 依頼時には、対応内容、採用・不採用の理由、実行した確認のコマンド・環境・結果を添える。
- Claude Codeが示した不足情報を補い、本文を自分で確認してからPRを作成する。

---

## Claude Code への作成指示

現在の作業ブランチについて、コミット履歴と差分を調査し、末尾の「PR 本文の雛形」に沿って日本語の PR タイトル案と本文案を作成してください。

このPRは、コードチェック課題のレビュアーが読みます。変更の目的、判断理由、外部仕様への影響等の概要が短時間で分かる文章にしてください。

### 1. 操作の範囲

- 今回は調査と文章案の提示だけを行ってください。ファイル編集、Gitの状態を変更する操作、PR の作成・更新・投稿は行わないでください。
- ビルド・テスト・静的解析は、この依頼だけでは新たに実行しないでください。

### 2. 調査する情報

- 現在のブランチ、HEAD のコミット SHA、作業ツリーとステージの変更状況を確認してください。
- ベースブランチは依頼で指定されたものを使ってください。未指定なら main を候補に、ローカル参照と既存 PR の取得可能な情報から妥当性を確認してください。曖昧なら質問し、別のブランチに黙って置き換えないでください。
- ベース参照がリモートの最新状態か確認できない場合は、その制約を本文外に明示してください。この依頼のために fetch や pull は行わないでください。
- 以下を基本に、読み取りコマンドで対象範囲を調査してください。<base> は確認したベース参照に置き換えてください。
    - git status --short --branch
    - git rev-parse HEAD
    - git log --format=fuller <base>..HEAD
    - git diff --stat <base>...HEAD
    - git diff <base>...HEAD
- 必要に応じて関連ファイル、対象 Issue、既存の ADR、私が共有した判断の記録・検証結果、対象コミットの CI 結果を読んでください。参照できない情報を読んだことにしないでください。
- 履歴から変更の経緯を、差分から最終的に残る変更を把握してください。途中で撤回した変更を最終成果として書かないでください。
- 未コミットの変更はコミット済みの PR 差分に含めないでください。

### 3. 記述の原則

- 冒頭で「どの問題を解決し、どういう状態になったか」を説明してください。
- 変更の短い要約は必要です。ただし、ファイル一覧や diff の逐語的な説明は避け、理由・判断・影響を中心に書いてください。
- コードから確認できる事実、私が共有した事実、推測を区別してください。理由が分からない場合、もっともらしい採用理由を作らないでください。
- 「検討した選択肢」には実際に検討した案だけを書いてください。今回初めて思いついた代替案を、過去に検討して不採用にした案として書かないでください。
- 「改善した」「安全になった」「テストしやすくなった」とだけ書かず、何がどう変わったかを具体的に示してください。効果を実測していない場合、実測済みの表現を使わないでください。
- 構造変更による仕様維持、バグ修正による挙動変更、UI 改善、新機能を区別してください。「仕様を維持する意図」と「実行して同じ動作を確認した事実」も区別してください。
- ビルド成功、テスト成功、端末上の動作確認を混同しないでください。テストコードや CI 定義があるだけで成功と書かないでください。
- コミットメッセージに「確認済み」とあるだけの場合は履歴上の記載として扱い、今回の最終差分の確認実績へ自動的に引き継がないでください。
- 技術仕様や互換性を断定する場合は、対象バージョンに合う根拠を確認してください。未確認の技術説明を確定した原因として書かないでください。
- エラーは判断に必要な箇所だけ原文で引用し、長いログは本文に貼り続けず、取得済みのログ等へ参照を付けてください。秘密情報は含めないでください。
- ADR に詳細がある場合は短く要約してリンクしてください。存在しないファイル、Issue、CI URL、プロンプトへのリンクを作らないでください。

### 4. 情報が不足している場合

- 分かる範囲で本文案を作り、判断理由の不足箇所は「要確認」と明示してください。任意項目に該当しない場合と、情報不足の場合を区別してください。
- 重要な不足情報は本文外にまとめて質問してください。確認できていない内容を埋めて、投稿可能な完成稿だと扱わないでください。
- CI 失敗や既知の不具合がある場合は隠さず記載してください。PR の作成可否とマージ可能な状態を混同しないでください。

### 5. 出力形式

1. 調査対象：ベース参照、HEAD の SHA、未コミット変更の有無、取得できなかった情報を短く示す。
2. PR タイトル案：変更の目的が伝わる短い日本語。Conventional Commits の type を付け、ビルド設定・依存の変更には build を使う。
3. PR 本文案：以下の雛形の順序で、コピーできる1つの Markdown コードブロックにまとめる。
4. 投稿前の確認事項：不足情報、確認してほしい記述を列挙する。なければ「なし」とする。

本文案から雛形の HTML コメントと空の行・表の行を取り除いてください。空行による段落の区切りは残してください。
任意セクションは該当しなければ省略してよいですが、必要なのに未確認の情報は省略しないでください。
